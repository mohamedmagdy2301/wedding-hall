## الخطوة 1.0 — قياس التشفير (D-58) ← توقف

نقاط قياس مؤقتة محمية بتوكن (كما في المرحلة 0، والتوكن يُولد في ملف مؤقت ولا يُطبع؛ مالك المنتج يضعه بـ `wrangler secret put`)، تُقاس على Workers الفعلي عبر `wrangler tail`: CPU لكل اشتقاق، نسبة النجاح، أخطاء الذاكرة (حد 128 ميجا لكل isolate — نفسه في الخطتين)، وزمن الاستجابة، وأثر كل مكتبة على حجم الـ Worker.

| المرشح | الإعدادات المقيسة | ملاحظات |
|---|---|---|
| Argon2id عبر `@phi-ag/argon2` (WASM SIMD، MIT، محدّث 2026-10) | OWASP: m=19 MiB, t=2, p=1؛ وإعداد أعلى (مثل m=46 MiB, t=1) | المرشح الأول |
| Argon2id عبر `argon2-wasm-edge` (MIT، مصمم لـ Workers) | نفس الإعدادات | آخر تحديث 2024 (صيانة أضعف) |
| scrypt عبر `node:crypto` (أصلي في workerd مع `nodejs_compat`) | مكافئات OWASP داخل حدود الذاكرة (مثل N=2^16,r=8,p=1 و N=2^15,r=8,p=3) | بلا مكتبة إضافية |
| PBKDF2-SHA256 100 ألف (WebCrypto) | — | خط الأساس من المرحلة 0 (≈24 مللي ثانية للاشتقاق) |

- **قيد مهم:** Workers يمنع تجميع WASM من بايتات وقت التشغيل؛ أي مكتبة لا تستورد `.wasm` كـ module تُستبعد.
- **المخرجات:** جدول أرقام لكل مرشح (CPU وسيط/p90/أقصى، الذاكرة، حجم الـ bundle)، وأثره على الدخول في الإنتاج (Paid) وعلى التطوير (Free)، والترشيح.
- نقاط القياس والتوكن تُزال بعد القرار.

## الملفات والوحدات

- `src/modules/auth/`: الدخول (موبايل أو اسم مستخدم — P1-03)، القفل بعد 5 محاولات لمدة 15 دقيقة برسالة عامة (SEC-03) مع تشفير وهمي عند عدم وجود المستخدم لمنع كشفه بالتوقيت، الجلسات (كوكي `HttpOnly`/`Secure`/`SameSite=Lax`، 7 أيام تتجدد — T-17)، تغيير كلمة المرور (8 أحرف على الأقل — SEC-02)، وحدة التشفير بمعاملات من البيئة و rehash (P1-08).
- `src/modules/users-rbac/`: قائمة الصلاحيات الثابتة، الأدوار الافتراضية، حساب صلاحيات المستخدم (اتحاد أدواره؛ المالك يملك الكل)، وقواعد BR-100 و BR-101 و BR-102.
- `src/modules/audit/`: `record(tx, …)` يأخذ Transaction العملية إلزاميًا، و `list(filters)`.
- `src/server/action.ts`: غلاف موحد لكل Server Action: **جلسة ← Zod ← صلاحية ← خدمة**، ويرجع أكواد API.md برسالة عربية.
- `src/server/dal.ts` (طبقة الوصول للبيانات): `verifySession()` مخزنة لكل طلب، تتحقق من الجلسة وحالة المستخدم في كل جلب بيانات (P1-07).
- `src/lib/phone.ts`، `src/lib/i18n/ar.ts` (نصوص المرحلة).
- `scripts/setup-venue.ts` + `npm run setup-venue`: المنشأة + المالك + الأدوار الافتراضية + الإعدادات الافتراضية (P1-01)؛ كلمة المرور من خانة مخفية (P1-02)؛ يرفض التشغيل إن وُجدت منشأة.
- shadcn/ui (P1-04) مع `DirectionProvider`.

## الاختبارات

- **وحدات:** تجميع الصلاحيات (والمالك يملك الكل)، توحيد الموبايل وصيغة الـ login، سياسة كلمة المرور، حساب القفل وانتهائه، قراءة/مقارنة معاملات الـ hash وقرار rehash، تنقية نص الدخول الفاشل قبل التسجيل (P1-06).
- **تكامل (PostgreSQL حقيقي):**
  - الدخول: نجاح، فشل، قفل بعد 5 محاولات، انتهاء القفل بعد 15 دقيقة، رسالة موحدة.
  - الجلسات تنتهي عند تعطيل المستخدم أو تغيير كلمة المرور (BR-101، SEC-04).
  - **مستخدم عُطّل وجلسته مفتوحة لا يجلب أي بيانات** (P1-07).
  - **لكل صلاحية حساسة في المرحلة: الطلب المباشر بدونها يُرفض** (SEC-11).
  - المالك لا يُعطّل، ومالك واحد على الأقل دائمًا (BR-100)؛ غير المالك لا يمنح ما لا يملكه ولا يلمس حساب مالك (BR-102).
  - فشل العملية يلغي سجلها (SEC-41)؛ الـ trigger يمنع تعديل/حذف السجل (SEC-42).
  - أحداث الدخول تحمل IP ونوع الجهاز ولا تحمل كلمة مرور أبدًا، والنص غير الصالح لا يُسجل (P1-06).
  - rehash عند تغيير المعاملات (P1-08).
  - `setup-venue` يرفض التشغيل مع وجود منشأة.
- **e2e (Playwright):** دخول بكلمة مؤقتة ← تغيير إجباري؛ إضافة موظف استقبال؛ موظف الاستقبال لا يفتح شاشة الموظفين؛ مكونات shadcn/ui تعمل صحيحًا في RTL على الكمبيوتر والموبايل (P1-04).

## ترتيب التنفيذ (commits صغيرة)

1. **1.0 قياس التشفير ← تقرير ← توقف وقرار.**
2. Migration الجداول + trigger السجل.
3. وحدة التشفير (حسب القرار) + الجلسات + DAL.
4. خدمات الدخول والقفل وتغيير كلمة المرور.
5. الصلاحيات والأدوار والمستخدمين + غلاف الـ Server Action.
6. سجل العمليات.
7. `setup-venue`.
8. shadcn/ui + الشاشات.
9. الاختبارات الكاملة ← مراجعة ذاتية ← تقرير ← توقف.

## تذكير بقواعد العمل (من المرحلة 0)

- الأسرار في `.env.secrets.local` و Worker secrets فقط (T-19)، ولا تُطبع قيمها أبدًا.
- أي أمر يحتاج إدخال قيمة سر (مثل `wrangler secret put`) يشغّله مالك المنتج بنفسه.
- `git push` فقط بعد موافقة مالك المنتج على commits المرحلة أو بطلب صريح.
- لا شيء من "خارج النطاق" في PRD.
